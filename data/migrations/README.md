# Миграция `teg` для практик

## Подписки: подготовленная миграция

`20261013_subscriptions.sql` создаёт отдельные таблицы подписок, заказов,
отправленных уведомлений и закреплённой практики дня. Она применена
**только к локальной `yogadaily_test`** 14 октября 2026 года и не запускается
автоматически ботом. Существующие пользователи не
записываются в подписки и не переводятся в бесплатный режим.

`20261020_readable_subscription_fields.sql` безопасно переименовывает поля
уже созданных таблиц в согласованные наглядные названия: `subscription_starts`,
`subscription_ends`, `subscription_state`, `base_price` и `final_price`.
Данные и значения цен не изменяются; миграция автоматически не выполняется.

`20261022_old_users.sql` готовит поля для разового переходного сценария
старых пользователей. Сама миграция не формирует группу, не выдаёт доступ
и не отправляет сообщения. Активация выполняется отдельно через
`tools/activate_old_users.py` с явной датой запуска и подтверждением.

`20261030_superseded_orders.sql` добавляет отметку для оставленных попыток
оплаты. Она позволяет после возврата к тарифам создать новый платёж с новой
суммой, не удаляя старый заказ и не теряя его, если покупатель всё-таки завершит
оплату по ранее открытой ссылке. Миграция не меняет статусы и суммы заказов.

Для другой БД отдельно выбрать окружение и проверить миграцию на нём.
Изменения production требуют отдельного подтверждения. Для сообщений об оплате
реализованы блокировка отправки между процессами и журнал событий. Журнал
заполняется после ответа Telegram; при потере ответа уже принятое сообщение
может быть отправлено повторно. Доступ при этом повторно не продлевается.

## Разделение тестовых и реальных заказов

Миграция `20261020_payment_scope.sql` подготовлена для разделения заказов
тестового магазина 1497096 и реального магазина 1495040 внутри локального
тестового окружения. Ограничена `current_database() = 'yogadaily_test'`.
Добавляет колонку, сохраняет историю и не меняет оплаченные сроки.
Применять с остановленными локальными ботом и платёжным backend; автоматически
не выполняется. Исторические заказы получают `test:1497096`.
После миграции требуется обновлённый код обоих процессов с одинаковым режимом.
Применена только к локальной `yogadaily_test` 20 октября 2026 года;
восемь исторических успешных заказов сохранены. Production не изменялся.

## Практики: существующая миграция `teg`

Подготовлена разовая миграция для таблиц `yoga_practices` и
`mood_practices`. Она добавляет поле:

```sql
teg TEXT[] NOT NULL DEFAULT ARRAY[]::TEXT[]
```

Для поиска создаются GIN-индексы. Заполнение берётся из
`20260824_practice_teg.json`: 68 yoga-практик и 31 mood-практика.
Заменённые дубли `yoga:13` и `yoga:78` намеренно исключены: миграция не
будет изменять их `teg`.

## Безопасный порядок запуска

1. Локально проверить структуру payload без подключения к базе:

   ```bash
   python3 tools/migrate_practice_teg.py --payload-only
   ```

2. Проверить payload и записи в выбранной базе без изменений:

   ```bash
   python3 tools/migrate_practice_teg.py
   ```

3. Убедиться, что проверка нашла все 99 ID и не обнаружила отличающиеся
   названия или ранее заполненные конфликтующие `teg`.

4. Только после отдельного подтверждения выполнить миграцию:

   ```bash
   python3 tools/migrate_practice_teg.py --apply --confirm APPLY_TEG
   ```

DDL, заполнение и финальная сверка выполняются в одной транзакции. При любой
ошибке транзакция откатывается. Без `--apply` скрипт выполняет только
read-only проверку и завершает соединение через `rollback`.

Флаги `--allow-title-mismatch` и `--allow-overwrite` ослабляют защитные
проверки; без отдельного осознанного решения их использовать не следует.
